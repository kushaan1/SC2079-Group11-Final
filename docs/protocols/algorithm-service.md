# Protocol — RPi ⇄ algorithm service (HTTP)

> The contract between the Raspberry Pi and the algorithms subsystem. Written down before either
> side is finished, per `AGENTS.md` §2.2 and §9.2 rule 6 — integration is where MDP teams lose the most
> time, and two subsystems must never agree on a format verbally.
>
> Implemented by `algorithm/app.py` + `algorithm/pathfinding_controller.py`. The machine-readable
> version is generated by the running server at `GET /openapi/openapi.json` and committed here as
> [`openapi.json`](openapi.json). **That file is generated — regenerate it, never hand-edit it.**
>
> Owner: algorithms. Raise changes with the RPi owner before making them.

## Endpoint

```
POST /pathfinding/          (trailing slash required)
Content-Type: application/json
```

Address is **not fixed**. The service binds `0.0.0.0` on port **5000** by default and logs the
exact URL to use on startup. Never hardcode it — the laptop's address is assigned by whatever
network the arena uses, usually the RPi's own hotspot. Override the port with `MDP_PORT` or
`--port`, not a code edit.

Interactive Swagger UI for poking at it by hand: `http://<address>:<port>/openapi/swagger`.

## Request

```jsonc
{
  "verbose": true,                    // optional, default true
  "robot": {
    "direction": "NORTH",             // NORTH | EAST | SOUTH | WEST
    "south_west": {"x": 0,  "y": 0},  // inclusive corners, centimetres
    "north_east": {"x": 30, "y": 30}
  },
  "obstacles": [                      // at least 1
    { "image_id": 11,
      "direction": "SOUTH",           // which face carries the image
      "south_west": {"x": 50, "y": 90},
      "north_east": {"x": 59, "y": 99} }
  ]
}
```

- Coordinates are **centimetres**, origin at the arena's south-west corner, and both corners are
  **inclusive** — a 10 cm obstacle spans e.g. 50..59, not 50..60.
- `direction` on an obstacle is the face the image is on; on the robot it is the heading.
- `image_id` must be **1–40**. It identifies the obstacle, not the image: on a real run it is the
  tablet's obstacle number (1–8), and it is echoed back unchanged in `segments[].image_id` and
  `unreachable[].image_id`. Hand-written arenas may instead use a real image ID (11–35 the digits
  and letters, 36–40 the arrows and stop marker). IDs outside 1–40 are rejected (see "Errors").
- `image_id` must be **unique** across obstacles.
- `verbose: false` omits the per-cell path and zeroes the cost. Use it once you no longer need to
  draw the route — a 4-obstacle verbose response carries ~1000 path vectors.

## Response — 200

```jsonc
{
  "segments": [                       // one per obstacle to visit, IN VISIT ORDER
    { "image_id": 12,
      "cost": 88,
      "instructions": [
        {"move": "FORWARD", "amount": 15},
        "FORWARD_RIGHT",
        {"move": "FORWARD", "amount": 10},
        "CAPTURE_IMAGE"
      ],
      "path": [ {"direction": "NORTH", "x": 15, "y": 15} ]   // truncated; 82 vectors
    }
  ],
  "unreachable": [                    // obstacles the robot will NOT visit
    { "image_id": 13, "reason": "NO_OBJECTIVES" }
  ]
}
```

### Instructions

Three token types, mixed in one list:

| Token | Meaning |
|---|---|
| `{"move": "FORWARD"\|"BACKWARD", "amount": <cm>}` | Drive straight. `amount` is centimetres, always ≥ 1 |
| `"FORWARD_LEFT"` `"FORWARD_RIGHT"` `"BACKWARD_LEFT"` `"BACKWARD_RIGHT"` | A quarter-turn arc |
| `"CAPTURE_IMAGE"` | Stop and photograph. **Terminates every segment** |

- Consecutive same-direction moves are already merged, so you will not receive two `FORWARD`s in a
  row.
- **A turn token carries no radius or angle.** Its geometry comes from the algorithm's
  `config.TURN_RADIUS_CM`, which is currently the *prior-year* team's numbers. The four directions
  have genuinely different radii and radius grows with speed, so these must be re-measured on our
  chassis — see "Open items".
- After `CAPTURE_IMAGE` the robot is nose-to-obstacle and the next segment begins with a reverse.

### `unreachable`

**Additive field, not present in the prior-year contract.** Every obstacle in the request appears
in exactly one of the two lists, so:

```
len(segments) + len(unreachable) == number of obstacles sent      // always
```

Without this field a dropped obstacle is invisible: the response simply has fewer segments than you
sent obstacles, and the explanation goes to stdout on the planning laptop. That is lost points with
no diagnostic.

**The two reasons are not interchangeable — please don't collapse them into one "failed" state:**

| `reason` | Means | Likely fix |
|---|---|---|
| `NO_OBJECTIVES` | No camera pose exists for that obstacle at all — it faces a wall it sits too close to, or a neighbour's keep-out swallows every approach | Algorithms geometry, or move the obstacle |
| `NO_PATH` | Poses exist, but this route could not reach them from where it left the robot | Algorithms routing |

Surfacing these on the tablet, even as "obstacle 13: unreachable", turns a mystifying run into a
diagnosable one. That is the whole reason the field exists.

⚠️ **Action for the RPi owner:** some OpenAPI generators produce models that reject unknown fields.
If yours does, this field will make previously-working responses fail to deserialise. **Please test
this before integration day** — if it is a problem, say so and it will go behind a request flag.
This is the highest-risk item in this document.

## Errors — 422

One shape for every validation failure, whether it came from schema checking or from the
algorithm's own rules:

```jsonc
[ { "type": "value_error",
    "loc": ["obstacles", 0, "image_id"],
    "msg": "image_id 41 is outside the valid range 1-40 (inclusive)." } ]
```

Read `msg` for something human-readable and `loc` for which field. `loc` keeps list indices as
integers (`0`, not `"0"`). Cases that return 422:

| Cause | `loc` |
|---|---|
| `image_id` outside 1–40 | `["obstacles", <i>, "image_id"]` |
| Duplicate `image_id` across obstacles | `[]` |
| Corners inverted or not square | `["obstacles", <i>]` or `["robot"]` |
| Robot or obstacle outside the 200×200 arena | `[]` |
| Empty `obstacles` list | `["obstacles"]` |

**No malformed request should ever produce a 500.** If you get one, that is an algorithms bug —
send the request body and it will be fixed.

## Stub mode

The algorithm can run as `python app.py --stub`, returning a **fabricated** schema-valid response
— one segment per obstacle, no planning. It exists so the RPi and Android work can be tested end to
end before the planner is finished.

- Stub responses carry the header **`X-MDP-Stub: true`**. Any test meant to exercise the real
  planner should assert that header is **absent**, so a forgotten flag cannot pass for a working
  system.
- `path` and `unreachable` are always empty in stub mode, even with `verbose: true`. Fabricated
  coordinates would let the tablet draw a route that looks plausible and is wrong.

**Do not drive the robot from stub output, and do not measure timings against it.**

## Deviations from the prior-year contract

The prior-year team's `openapi.json` is what an earlier generated client was built from. The
**request shape is unchanged**, so such a client still works. Five things differ, all additive or
error-path only:

| # | Delta | Breaks a client? |
|---|---|---|
| 1 | `unreachable` response field added | **Possibly** — see the warning above |
| 2 | Duplicate `image_id`s rejected with 422 | No. Never a legal arena |
| 3 | An `image_id` outside 1–40 returns 422 instead of 500 | No. Schema still declares `minimum: 1`; the narrower 1–40 rule is enforced below it and mapped to a clean 422 |
| 4 | 422 bodies use `type`, not `type_` | Only if you parse 422 bodies. The prior-year schema did not match its own framework's output; ours matches what is actually emitted |
| 5 | `image_id` 1–10 accepted (was 422) | No. The field is the tablet's obstacle number, which starts at 1 |

Rationale for each is in [`algorithm/PROVENANCE.md`](../../algorithm/PROVENANCE.md) under "Design
decisions".

## Open items — need another subsystem's input

1. **RPi:** does the generated client tolerate the unknown `unreachable` response field?
2. **RPi:** is port 5000 correct? It is a placeholder.
3. **STM:** the four measured turning radii — forward-left, forward-right, backward-left,
   backward-right — at competition speed, on our chassis. Every plan is only as accurate as these,
   and the current values are another team's car.
4. **CV:** the authoritative camera standoff distance. The course documents state it three
   inconsistent ways (~20 cm optimum, a 25–30 cm band, and two disagreeing formulas). The planner
   currently uses 25–30 cm.
